# 角色卡工作台：让卡从黑盒变成可见、可编辑的作品

2026-09-09 用户提出���写卡模式已经解决「agent 能不能动卡」，没有解决「卡是什么、动了哪里、动完什么样」。本文是计划，不是实施记录；按 AGENTS.md 铁律，用户说「开始」之前只做只读工作。

## 一、问题定性

现在三方看到的卡各不相同：

- 模型看到 `card_project` 的资源列表——`field / greeting / lore / script / regex-pattern / regex-template` 六种，按 JSON 路径切出来的字符串槽位。
- 用户在「角色卡 → 代码与资源」看到同一份源码列表，逐个文件点开读，和看仓库无异。
- 磁盘上仍是仿酒馆的一张 PNG/JSON 放��� `cards/<目录>/`，外加 `创作/` 工程做快照与源文件。

所以「黑盒」不是展示层没做好，而是**梨园没有自己的角色卡数据模型**：卡一直被当作酒馆格式的不透明包裹，只在边缘解包/回写。第一切片「映射由快照决定、不按作者标题推测用途」在保真上正确，但也等于主动放弃理解卡。写卡模式扩展了工具，工具落点却无法被用户看见；agent 的修改过程与效果都不直观。

参考物：墨月写卡器在线版（用户截图，2026-09-09）。它把一张卡按**作者心智**拆成十个板块，每块带状态：`00 作品设置 / 01 人物 / 02 世界书 / 03 创作规则 / 04 开场白 / 05 MVU 变量 / 06 状态栏 / 07 消息前端 / 08 EJS / 09 检查与导出`，中间是当前板块的表单编辑，右侧 AI 解答区。值得借的是左栏那份目录——它就是「一张卡里有什么」的答案，而且与 spec 字段不是一一对应（状态栏和消息前端在 spec 里都是正则＋HTML＋脚本的混合物，MVU 散落在世界书条目与 prefault 脚本里）。

## 二、目标

内置一个**角色卡工作台**：用户能按板块看见并手动编辑一张卡的全部构成；agent 通过工具编辑同一份数据；agent 的每次修改能在界面上定位到板块与 diff。

不做的事：账号、作品库、在线保存等平台件（卡空间已是每卡一文件夹）；右栏独立 AI 助手（梨园 agent 就在主会话）；替换 PNG/JSON 作为互操作格式；新的提示词/注入通道；靠作者措辞归类资源（铁律三）。

## 三、四步

| 步 | 工作 | 产出 | 验收 |
|---|---|---|---|
| 1 | 继续探查写卡平台 | 板块目录与每块的字段/交互清单；平台把 spec 字段怎样归组 | 清单能回答「某板块由哪些 spec 字段构成」 |
| 2 | 读真卡，弄清一张卡的构成 | 样本清单；逐卡构成表；**板块 ↔ spec 字段映射表**及归不进去的余项 | 每张样本卡都能按映射表无损分到板块，余项有列举 |
| 3 | 搭工作台的服务层 | 卡→板块投影、板块状态、agent 工具走同一入口、只读校验视图 | 22 张卡逐张打开，投影与第 2 步构成表一致 |
| 4 | 写前端 | 板块编辑、手编/agent 共用保存通道、修改高亮与 diff | 用户手编 → agent 改 → 用户看见落点，导出再导入一致 |

### 步 1 与步 2 并行，互为验尺

只看平台会照搬别人的分类；只看卡会退回 JSON 路径的资源列表。两边一起做，产出一份映射表：每个板块 ← 由哪些 spec 字段/**结构判据**构成。结构判据指 spec 自带的字段：正则的 placement（送模/显示）、替换内容是否含 HTML、脚本的挂载位置与来源命名空间、世界书条目的 position/depth/constant、prefault 脚本签名。作者给的标题/注释只作展示，不作归类依据。归不进去的放「其他资源」，由用户或 agent 手动归位并落成数据（`创作/manifest.json` 或同级文件）。

步 1 的材料：墨月在线版（截图＋用户账号可继续浏览其余板块）、本机墨月工程包、tavern-cards 的 manifest 设计，以及 `%TEMP%\liyuan-card-authoring-20260908\梨园写卡能力调查-2026-09-08.md` 已有结论，不重做已完成的部分。

步 2 的样本按四类各至少一张，由用户从 `cards/` 的 22 张中圈定（卡名不进仓库，清单放 `.liyuan-artifacts/card-studio/samples.md`）：

- 纯文字卡：零脚本零正则。验证投影不会把简单卡撑出一堆空板块。
- 轻前端卡：状态栏靠正则＋HTML，无页面脚本。
- 重前端卡：页面级脚本、外部依赖或远程引用、多正则协作。
- MVU 卡：变量 schema/初值/更新规则齐全，是「MVU 变量」板块的唯一真实来源。

每张卡记录：spec 版本、字段清单、世界书条目数与 position 分布、正则数与 placement、脚本数与来源、变量结构、开场数，以及**哪些内容按映射表归不到板块**。

### 步 3 与步 4 的边界按「服务／视图」切

步 3 产出语义层服务：建立在 `src/card-authoring.ts` 之上，把资源投影到板块，加板块状态（有无、条数、最近修改来自用户还是 agent）。`card_project` 与面板已共用这一份服务和 hash 冲突保护，新增只是投影，不另起存储。步 3 **必须带一个只读界面**——左栏目录＋点进去看原文（复用现有编辑器）——否则投影无法逐卡校验。

步 4 才是完整编辑体验：板块内表单/编辑器、手编与 agent 共用 write/check/apply、用 `liyuan-process` 里已有的工具回执把 agent 的每次修改映射到板块高亮与 diff。

### 存储先不动

PNG/JSON 仍是导出物与互操作格式，`创作/` 工程仍是真源；板块投影是对工程源文件的一层视图，不改磁盘布局，第一切片的保真承诺不受影响。投影稳定后再评估「梨园自己的卡格式」是否值得。

## 四、铁律自检

- 铁律一/二：不改任何送模文案，不增注入点。板块投影只服务用户界面与 `card_project` 的返回结构。
- 铁律三：归类只用 spec 结构字段，不建标题/措辞名单；余项显式列出并交给数据。若某板块只能靠猜名字才能填，宁可留空。
- 铁律四：问题全集＝任意酒馆 v2/v3 卡；负责人＝`card-authoring` 服务的投影层；没见过的卡的表现＝按映射表分板块、余项落「其他资源」，不静默丢弃。

### 正则的位置（2026-09-09 定案）

正则是酒馆的翻译文件，梨园为兼容导入卡必须读懂它（现状 `cardfront.ts` 已对齐），但它不是梨园的创作概念。五张样本的界面正则全是「find＝一个标签或占位符，replace＝模板，placement 2，markdownOnly」；梨园原生绑定定为这一子集：**标签 → 模板**。导出酒馆格式时逐条编译成正则，导入时反向解回；解不回的保留为「原样正则」不强翻。超出子集的能力（harness 直接喂数据、组件调用工具）等真需要时再加，加时必须回答导出酒馆如何退化。工作台里正则不露面：界面板块显示组件绑定，文本正则板块显示「对模型隐藏」。优先级不高，步 3 只在 facts 里记判据。
