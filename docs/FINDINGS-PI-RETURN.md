## 问题一：梨园没有项目分层——每一张角色卡不是一个工作空间

### 用户的判据（2026-09-05 原话大意，本条的定性以此为准）

> 一切都要回归于后端来看。我们平时用 Claude Code 是怎么样的？在项目的那个文件夹里面打开终端，
> 输入 `claude`，启动 CLI，**此时这个文件夹就变成了我们的工作空间**。梨园也应该如此——
> **每一张角色卡在梨园的后端里面就应该代表着一个文件夹，代表着一个工作空间。**

这是一条**架构判据**，不是一个功能诉求：agent 的一切分层（身份、项目约定、技能、资料、可写工件、
会话历史）在 coding agent 里都锚定在「cwd＝工作空间」这一个事实上。没有这个锚，分层无处可挂。

### 现状实证（本窗口读码坐实）

梨园现在是**一个扁平的单项目**：

- 一个工作目录（`cwd`），底下一排兄弟目录装全部数据：`src/paths.ts` 的 `DIRS` ＝
  `.liyuan-state` / `.liyuan-lore` / `.liyuan-media` / `.liyuan-skills` / `.liyuan-worldline` /
  `.liyuan-memory` / `.liyuan-artifacts` / `.liyuan-assistant` / `.liyuan-cache` / `.liyuan-uploads` /
  `.liyuan-audio`。
- **卡是这个目录里的文件**，不是目录：`src/card.ts:105` `loadCardFile(path)` 按文件路径读卡。
- 卡与会话的关联靠**路径字符串比对**：`src/paths.ts` 的 `sameCardPath(a, b, projectCwd)`
  （兼容相对/绝对、反斜杠、`./` 前缀、盘符大小写）——会话列表按这个函数过滤属于哪张卡。
- 预设也是全局单份：`PRESET_FILE = "liyuan-preset.json"` 在项目根。

⇒ 全部卡共用同一个状态池、同一个世界书池、同一个技能池、同一份预设、同一个记忆库；
「属于哪张卡」是**事后用字符串筛出来的**，不是**结构上分开的**。

### pi 侧的对照机制（本窗口读源码实证，0.80.3 与 0.84.4 一致）

pi 的分层全部锚在 cwd 上，而且三个格子的**作用域合并规则各不相同**，这正是梨园完全没有的东西：

| 格子 | 作用域规则 | 源码位置 |
|---|---|---|
| `SYSTEM.md`（替换基座） | **赢者独占**：项目 `.pi/SYSTEM.md`（需 trusted）盖全局 `~/.pi/agent/SYSTEM.md`，只有一份进提示词 | `core/resource-loader.ts` `discoverSystemPromptFile()` |
| `APPEND_SYSTEM.md`（追加） | **赢者独占**：同上；且 `--append-system-prompt` 一给，文件**根本不读**（源码是 `??` 不是拼接） | `discoverAppendSystemPromptFile()`；`resource-loader.ts:483` |
| `AGENTS.md`（项目上下文） | **唯一真正叠加**：先全局，再从文件系统根一路走到 cwd，每层有就收一份，按路径去重 | `loadProjectContextFiles()`（`resource-loader.ts:84`） |

补充两条同样锚在 cwd 的：

- 同一目录里只取一份上下文文件，顺序 `AGENTS.override.md` → `AGENTS.md` → `AGENTS.MD` →
  `CLAUDE.md` → `CLAUDE.MD`。⇒ **`AGENTS.override.md` 只切断自己这一层**，别的层照叠。
  （`override` 是 0.84.0 新增，梨园 vendored 的 0.80.3 还没有。）
- skills 是**累加**：全局 `~/.pi/agent/skills/`、`~/.agents/skills/`，项目 `.pi/skills/`，
  以及**从 cwd 到 git 仓库根逐层**的 `.agents/skills/`，再加包、settings、CLI。prompts 模板同理。

### 缺了这一层，梨园结构上做不到的事（现象，非方案）

1. **没有「这张卡不继承那条全局偏好」的表达方式**。pi 靠某一层放一份 override 就切断，梨园无此概念。
2. **卡与卡之间没有隔离**：技能、世界书、记忆、预设都只有一个全局池，靠命名和过滤区分。
3. **没有「一局」这一层**：世界线是数据不是目录，无法让某一条世界线带自己的资料。
4. **卡的资料无处安放，只能被塞进提示词**：`src/stage/assemble.ts` 的
   `buildStageSystemPrompt` 现在要亲手拼「角色卡兜底段」「用户扮演谁」「常驻世界设定」——
   在 pi 里这些本是 `AGENTS.md` 层的内容，由 cwd 决定加载哪几层，harness 不必逐段拼。

### 代价预告（只作记录，不构成方案）

改成「卡＝目录＝工作空间」不是换个说法：`sameCardPath` 那套过滤要整体重写；已有数据要迁移；
备份 / 导出 / 导入三条路径（`src/backup.ts`）都要跟着改。**这本身是一次结构手术，不是提示词分层的附带工作。**

## 问题二：预设的去处——它有架构，但只有位置轴，没有性质轴

### 用户的提问（2026-09-05）

> 第二个问题自然就是预设的去处了。我们得分析现有预设，分析他们在梨园里面的最终提示词形态，
> 到底**为什么预设相比于普通的提示词的污染会这么大**，预设**有没有一个明确的架构供我们拆分**。

### 语料与方法

三份真实预设（本机 `E:\新建文件夹 (10)`）：TGbreak V2.1.6、狐神抚 V18.7、双人成行 v10.0。
按梨园自己的装配语义复算（`src/preset-assemble.ts`：`prompt_order` 定序 + `enabled` 过滤 +
`marker` 归位 + `chatHistory` 切前后段）。脚本 `_preset-anatomy.mjs`（`_*` 已 gitignore，可复跑）。

### 一、预设确实有明确架构，但它是**位置架构**

机器可读的结构字段（酒馆自己发行的协议，闭合集，铁律三允许认的那一类）：

- `prompts[]` 按 `identifier` 存块定义；
- `prompt_order[]` 按 `character_id` 给次序 + 每块 `enabled`；
- `marker: true` + 八个内置槽位（`worldInfoBefore` / `charDescription` / `charPersonality` /
  `scenario` / `worldInfoAfter` / `personaDescription` / `dialogueExamples` / `chatHistory`）；
- `role`（system / user / assistant）；
- `injection_position` / `injection_depth` / `injection_order`。

这个轴能可靠回答四件事：**每块在哪、开没开、梨园的料该填进哪个位置、谁是预填**。
它**回答不了**任何一块「是什么性质」。

### 二、实测：位置轴与内容性质**零相关**

| 预设 | 总块 / 启用 / 启用字数 | `chatHistory` 位次 | before 段 | after 段 |
|---|---|---|---|---|
| TGbreak V2.1.6 | 99 / 53 / 11314 | 第 16 | 15 块 1605 字 | 37 块 **9709** 字 |
| 狐神抚 V18.7 | 215 / 62 / 12823 | 第 50 | 49 块 **11635** 字 | 12 块 1188 字 |
| 双人成行 v10.0 | 250 / 78 / 19820 | 第 33 | 32 块 10512 字 | 45 块 9308 字 |

同一类内容（文风 / 破限 / COT / 禁词）在三份预设里的位置完全不同：**TGbreak 86% 的字在历史之后，
狐神抚 91% 在历史之前，双人成行五五对半**。⇒ **按位置拆，拿不到任何内容层面的分离。**

### 三、`role` 轴是空的

启用块几乎全是 `system`。非 system 的实体块每份只有 1~3 个，且只有两种固定用途：

- **破限信件对**：TGbreak `user:miumiu~`(234) + `assistant:ฅ^•ﻌ•^ฅ`(56)；双人 `assistant:🔒 ┣ 双人出发`(824)；
- **末条预填**：狐神抚 `assistant:--直出输出(顶think标签)`(49)；双人 `assistant:✨丨Gemini`(118)。

⇒ role 不是分类轴，是**两个特定机关**的实现细节。

### 四、深度注入轴是空的

三份预设 `injection_position=1` 全部 **0 块 0 字**。此前记忆已记「深度注入实测零分量」，
三预设坐实。⇒ 这条轴不存在，别再为它设计机制。

### 五、`regex_scripts` 三份全为 **0 条**——需修正旧认知

此前的理解是「预设自带 `regex_scripts`，它是显示层的主人，六层名单都是它的替代品」
（记忆 `liyuan-preset-regex-channel`）。**在这三份语料上不成立**：显示正则来自**卡**，不是预设。
⇒ 「预设带正则」不是普遍事实，至少不是这三份主流预设的事实。

### 六、作者真正的架构写在**块名**里，而那正是 harness 不许读的通道

- 权限标记：`🔒`（别动）、`✔️`（必开）、`😾😾别关`、`初始化(不要关)`、`🔒 ┗ 尽可能不要动（变量组）`；
- 分组用制表符画括号：`🔒 ┏` / `🔒 ┣` / `🔒 ┗`；
- 用途前缀：`cot-`、`👻`/`🥵`（NSFW）、`🚫`（禁用词）、`♻️`（防打断）、`👁️🔒`（防全知）。

⇒ 作者**确实在声明结构**，但声明在 `name` 字段的散文与 emoji 约定里，**每个作者一套**，
且铁律三明令 harness 不认作者措辞。这个轴既不可用，也不该用。

### 七、为什么污染比普通提示词大——六条机制，全部有数

| # | 机制 | 数据 |
|---|---|---|
| a | **量级压倒** | 预设启用字数 11314 / 12823 / 19820；梨园自己在 system 里的固定文案合计 **676 字**（`buildStageSystemPrompt` 全部模板字面量剥掉插值后实测）。**比值 17:1 到 29:1**。每拍注入的梨园固定文案另 **181 字**。⇒ 同一个 system 里，梨园的声音是零头。 |
| b | **占的是身份格** | 11k~20k 字以祈使句写成，与 harness 自己的话**同级、无出处、无包裹**。pi 的项目资料有 `<project_instructions path=…>` 包着；预设什么都没有。⇒ 模型分不清「我是谁」与「别人给我的资料」。这是「已识别 A」的量化证据。 |
| c | **它是运行时，不是文档** | 狐神抚「思维链（多角色内心OS）」3342；双人「变量组」3180 +「思考模式（繁）」1698；TGbreak「cot-基础思维-必开」826 +「检查格式」620。这些不是内容，是**在没有 harness 的酒馆里用提示词模拟出来的引擎**。梨园也有引擎。**两台运行时抢同一个循环。** |
| d | **它横跨生成点两侧** | 普通提示词只占 system；预设占 system（before）**＋ 历史之后**（after）**＋ 生成点前的预填**（末条 assistant）。8/22 两次实弹已证：动 after 段的位置直接把整拍打挂。⇒ 对生成的控制力比任何普通提示词高一个量级。 |
| e | **无差别常驻** | 启用块 **100% 每拍全量入场**，格式里没有任何按需机制。对比 pi 的 skills：只进索引，正文按需 `read`。 |
| f | **性质轴不存在** | 于是无法只让一部分入场——这一条把 a–e 全部锁死。 |

### 八、本条的结论：可拆的只有位置，不可拆的是性质

预设格式里**根本没有「性质」字段**。8/03 的九性质分类学（`docs/PRESET-SPLIT-TAXONOMY.md`
A–I 九类）是**人工逐块看出来的**；8/14 AI 分拣**证伪**；8/16 定纲「预设＝源码，不许纠缠」。
⇒ 任何「按性质拆预设」的方案都要重新踩 8/14 的坑。**这正是 1.4→1.5 最后只能整份加载的原因，
不是当时偷懒。**

> **⚠ 2026-09-05 晚收窄**：「8/14 证伪」实际压着四件事：脚本分类器真死；无人值守 AI 分拣在破限红线上
> n=1 错过一块；「预设→skill」送达是投影不是转换，故「拆开能否减轻污染」**从未端到端测过**；8/12 收缩
> 是复杂度疲劳。**被证伪的是自动、无人值守、连带整套送达机器的拆法；窄、保守、一次性、用户过目、
> 只走酒馆自带 `enabled` 开关的拆法没有被测过。** 上一行「必重踩 8/14 的坑」说过头了。

⇒ 若「预设的去处」要有解，数据指向的自由度只剩一个：**整份换格子**——一次位置变更，
不需要判断任何一块的性质。

> **⛔ 这个「整份换格子」的结论已在问题三被用户推翻**：现有位置对比酒馆**是正确的**，
> 换格子会破坏「忠实兼容酒馆」这条合约。本节结论请连同问题三一起读。

## 问题三：预设 ＝ 酒馆的 SYSTEM.md ＋ settings.json ＋ 一部分引擎——所以「挪位置」解不了

### 用户的定性（2026-09-05 原话大意，本条以此为准）

> 预设本质上就是**相对于酒馆那个软件**来设计的，他不是普通的提示词，他还**附带了部分 harness 的
> 特性，或者说模拟了**。另外酒馆也不是 agent，但如果拿酒馆来类比 agent，那么**预设在酒馆的地位
> 其实就是 SYSTEM.md**。这也是我们最大的一个难点——预设的处理问题，**不是简单挪一个位置**，
> **现有的位置如果对比酒馆其实是正确的**。

### 一、格式层面坐实：预设自带「基座」那一格

酒馆四个内置 identifier，三份预设**全部定义**（脚本 `_preset-builtin.mjs`）：

| 预设 | `main`（Main Prompt＝基座） | `nsfw` | `jailbreak`（末端指令） | `enhanceDefinitions` |
|---|---|---|---|---|
| TGbreak V2.1.6 | 403 字 **启用** | 61 停用 | 345 **启用** | 99 停用 |
| 狐神抚 V18.7 | 4 字 停用（**故意清空**） | 4 停用 | **1101 启用** | 4 停用 |
| 双人成行 v10.0 | **2693 字 启用** | 824 启用（role=assistant） | 236 启用 | 0 启用 |

双人成行的 `main` 就是问题二 top8 里那个 2693 字的 `🔒 ┏ 双人成行（Atri&Deach）`；
狐神抚把 `main` 清空到 4 字停用、改把 1101 字塞进 `jailbreak`。
⇒ **「预设＝SYSTEM.md」不是类比，是格式设计**：格式里**预留了基座那一格**，作者要么填满它，
要么故意腾空改用别的格。梨园把预设放在基座位置，**对比酒馆是正确的**。

### 二、它还自带一份 harness 配置：43~45 个顶层非提示词字段

三份预设的顶层字段（除 `prompts` / `prompt_order`）43、45、43 个，分三类：

- **采样**：`temperature` / `top_p` / `top_k` / `top_a` / `min_p` / `repetition_penalty` /
  `frequency_penalty` / `presence_penalty`；
- **上下文**：`max_context_unlocked` / `openai_max_context` / `openai_max_tokens`；
- **行为 harness**：`names_behavior` / `send_if_empty` / `impersonation_prompt` /
  `new_chat_prompt` / `new_group_chat_prompt` / `new_example_chat_prompt` /
  `continue_nudge_prompt` / `group_nudge_prompt` / `wi_format` / `scenario_format` /
  `personality_format` / `assistant_prefill` / `assistant_impersonation` / `stream_openai` /
  `tool_reasoning_mode`。

第三类**不是内容，是引擎行为**：世界书怎么排版、用户空输入时送什么、续写用哪句话、要不要预填、
名字怎么落进消息。⇒ 用 pi 的话说，**一份预设更接近一整个 `.pi/` 目录，而不是一个提示词文件。**

**所以预设是三件东西合一**：① 一个基座（`main` 槽）② 一堆内容块（作者自定义，位置由
`prompt_order` 定）③ 一份 harness 配置（43~45 顶层字段）。**普通提示词只有第 ② 件。**
这就是「为什么它不是普通提示词」的格式级答案。

### 三、梨园今天的兼容是「部分兼容」，而且**已经主动违约过一次**

实测梨园**读了什么**：`prompts` + `prompt_order` + `marker` 八槽位 + 采样七项（`src/samplers.ts`）。

**没读**（逐字段 grep 命中 0）：`impersonation_prompt` / `continue_nudge_prompt` /
`new_chat_prompt` / `group_nudge_prompt` / `wi_format` / `scenario_format` /
`personality_format` / `assistant_prefill` / `names_behavior` / `send_if_empty` /
`openai_max_context` / `nsfw` / `enhanceDefinitions`。
`main` 也没有特判——当普通块按 `prompt_order` 排（这一条恰好是忠实的：ST 里 `main` 本就只是
order 里的一块）。

**已有的一次主动违约（用户定案，不是疏漏）**：末条 assistant ＝酒馆预填位（`addAssistantPrefix`），
**梨园整块丢弃**（`src/stage/engine.ts` 注释：8/23 用户定案；「降级成 user 是假动作，role 变了那段字
仍顶在生成点前」）。理由是预填让 provider 把整段输出判成思维链，正文全丢。

⇒ **「忠实兼容酒馆」这条合约今天并不是绝对的**：在「保真会毁掉正文」的那一处，梨园已经选了不保真。
**这是先例，不是方案。**

### 四、真正的难点：两份互斥合约签在同一块地上

- **合约 A（2026-08-16 定纲，`liyuan-preset-is-source-code`）**：梨园＝酒馆的**兼容编译器**，
  忠实实现装配/求值/渲染算法；判据「差异一定出在兼容层算得不对」。
- **合约 B（2026-08-03 RP agent 化，`docs/PLAN-RP-AGENT.md`）**：梨园＝一个 **agent**，
  有自己的身份、循环、工具、工件。

在 `main` 那一格上：**A 说这块地归预设作者**（酒馆就是这么设计的，梨园现状正确）；
**B 说这块地归 harness**（agent 的身份不能让）。**两份合约从未被调和。**
**1.5 的处置是不声不响地放弃 B**——这就是「完善但不满意」的确切来源。

### 五、为什么同一份文件在酒馆无害、在梨园致命

酒馆**没有身份格要保护**，因为**酒馆不是 agent**——它是提示词装配器加显示管线，
它的基座是**设计上的真空**。预设填的是真空。
梨园**有**身份，同一份文件填进来就不是填真空，是**驱逐**。

> **同一份文件，在酒馆填的是真空，在梨园挤掉的是自我。**

⇒ 所以这**不是位置问题**（挪到哪一格都一样），是**同一个格子有两个合法主人**的问题。
**位置是症状，双主人是病。**

### 六、本条排除掉的三条路（有数据/先例支持，非方案）

1. **排除「整份换格子」**——这是我在问题二末尾给的结论，**在本条被用户推翻**：换格子破坏合约 A，
   而合约 A 是预设生态的门票。
2. **排除「按性质拆」**——问题二已排除（性质轴不存在，8/14 AI 分拣已证伪）。
3. **排除「加提示词把身份找回来」**——违铁律一；且量级上是 676 字对 11314~19820 字。

⇒ 三条路排除之后，本条只留一个**定性**（不是方案）：**问题不在 system prompt 这一层的排布上。**

## 附录一：pi 的提示词分层（标尺，实证）

装配点只有一个：`core/system-prompt.ts` 的 `buildSystemPrompt`，八格，顺序写死，末尾永远是日期+cwd。
`BuildSystemPromptOptions` 字段在 0.80.3 与 0.84.4 **完全一致**（这四个版本 pi 一格没加）。

1. **内置基座**——身份 + `Available tools` + `Guidelines` + pi 文档路径。
2. **customPrompt**——整体替换基座。来源 `--system-prompt` / `.pi/SYSTEM.md` / `~/.pi/agent/SYSTEM.md`。
3. **appendSystemPrompt**——追加。与替换是**两个独立字段**：替换了基座，追加照样接在后面。
4. **toolSnippets**——`Available tools` 里每工具一行；**只有给了 snippet 的工具才露面**（工具可挂着而在提示词里隐身）。
5. **promptGuidelines**——`Guidelines` 项目符号，**唯一来源是工具定义自己声明的**
   （`core/tools/read.ts:214`、`edit.ts:299`、`write.ts:192`），按活跃工具收集 + 去重；
   **工具不活跃，它那条自动消失**。另有两条永远在。
6. **contextFiles**——`<project_context>` / `<project_instructions path=…>` 包裹，按目录层级叠。
7. **skills**——`<available_skills>` 只放 name/description/location，正文靠模型自己 `read`（渐进披露）；
   可声明 `disableModelInvocation` 从索引隐身；**没有 read 工具时整段不注入**。
8. 日期 + 工作目录。

另三族：**每拍层**＝扩展 `before_agent_start` 链式改写 systemPrompt + 可注入一条带 customType 的持久消息。
**消息层**（不进 system）＝prompt 模板、`/skill:name`、`sendMessage`/`appendEntry`、
`context` 钩子重写整份消息列表（**改副本、不落会话**）。
**旁路层**＝压缩自带 `SUMMARIZATION_SYSTEM_PROMPT` + 首次/合并两套指令、分支摘要、轮次前缀摘要；
工具 description/schema 走 API `tools` 字段，不进 system 文本。

**第 5 格是全档最重要的一条对照**：说明书跟着工具走，工具下场它自动消失。
这是铁律一「先问删掉哪句能解决」的**架构答案**——句子不是靠人删的。

## 问题四：装配后的形态与「能不能拆」——分预设，可测

> 2026-09-05 用户点破：**当年（8/12~8/14）分拣处理的是导入的那份 JSON 全集；今天要处理的是
> 经酒馆引擎模拟装配后的提示词。两者不是同一难度的东西。**

### 一、装配把问题缩小了一个量级（本窗口实测，脚本 `_assembled-anatomy.mjs`）

| 预设 | 装配前（当年分拣的喂料面） | 装配后（今天真送模） | 块数收缩 | 字数收缩 |
|---|---|---|---|---|
| TGbreak V2.1.6 | 99 块 / 30722 字 | **38 段 / 9743 字** | 38% | 32% |
| 狐神抚 V18.7 | 215 块 / 110345 字 | **11 段 / 10018 字** | 5% | 9% |
| 双人成行 v10.0 | 250 块 / 113310 字 | **28 段 / 10393 字** | 11% | 9% |

装配吃掉的是：停用块（不在场）、纯 `setvar` 块（求值后零字，狐神抚启用 54 块只剩 11 段实体）、
宏协议本身（变量表已定值 17 / 60 / 131 个键）。**每段仍带作者写的块名**，不是匿名文本团。

### 二、引擎条落在哪一段（脚本 `_engine-locate.mjs` / `_engine-snip.mjs`）

签名取自 8/12 逐块取证的**原文**（思考量地板 / 排练协议 / 一次性输出格式 / 自检验算），
**不是新造名单**；只做定位不做分类。

| 预设 | 命中段 | 命中字数 | 占装配后 | 形态 |
|---|---|---|---|---|
| TGbreak | 5 段 | 852 | **9%** | 全是小段，最大 501 字 |
| 双人成行 | 3 段 | 1792 | **17%** | 477 字那段即 8/16 查实的 `at least 3500 tokens` |
| 狐神抚 | 2 段 | 9199 | **92%** | 其中一段 **6695 字**，段级切不开 |

摘出的原文样本：`每次回复前，你必须参考<draft>里每一项的每一个要点进行深度梳理`、
`铁律自检（生成前必须执行）逐句扫描输出文本`、`模拟段落 / 草稿优化`。

### 三、结论：可拆性是**分预设的**，且**可测**

- 两份预设的引擎是**几个带名字的小段、不到两成**，剩下的段干净 ⇒ 段级挑得出来，
  **不需要判断内容性质，只需要认那几段**。
- 一份预设作者把东西全写在一个 6695 字的块里 ⇒ **段级切不开，切就得切进块内部＝8/14 的坑**。
- ⇒ 判据：**装配后测一次就知道；测不出来就退回整份加载（＝今天的行为，不倒退）。**
- ⚠ 已知隐患：命中 ≠ 整段是引擎。对小段两者接近；对 6695 字大块只说明"里面有"，不说明比例。
  故「段级可拆」必须带**尺寸门槛**（超过某字数的段一律不动），门槛值未定。

### 四、同时修正的两条旧账

1. **「8/14 证伪按性质拆」说过头了**（已在问题二处收窄）：真死的是脚本分类器与无人值守 AI 分拣；
   「窄、保守、一次性、用户过目、只走酒馆自带 `enabled` 开关」的拆法**从未被端到端测过**——
   因为当年「预设→skill」的送达是投影不是转换，块从没上过货架。
2. **通道决定身份，不是文件决定身份**（本窗口实证）：右栏助手**看得见预设也看得见正文**，
   照常输出——预设经**工具结果通道**以块清单形态到达（`server/assistant.ts:384`）。
   **同一份文件走数据通道是材料，占系统槽位就接管运行时。**
