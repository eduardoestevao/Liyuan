## 3. 拍内闭环的具体证据

普通卡的交互拍只要求介绍眼前两条路、给几个具体走法。模型自主检索后写出 **273 字**上文，再调用 `ask`；等待时，稿件已经持久化为 `v1`。

测试用户用自由回答改变方向：先不过河，返回档案室处理湿簿，同时引用刚才的一句话要求语气更柔和。模型随即自主读技能、读稿、读取技能引用、局部修改、查询器具、续写和收笔。

- `draft_edit` 使用实际读到的 `v1`，只修改一个唯一原文锚点。机械核对：除该句外，已经写下的上文逐字保留。
- 随后的续写落实返回档案室的选择，没有继续走原来的渡船或石桥路线。
- 从提问、回答到收笔，稿件 ID 始终相同；最终 `v3`、574 字。显式写操作 2 次（改稿、续写），宿主代收 1 次（提问前正文），不把代收伪装成模型调用 `draft_write`。
- 下一拍实际 HTTP 请求里的历史包含完整 574 字定稿：旧句已替换，改道后的后半段也在。不是仅仅在前端看到了新稿。
- 本轮没有生成计划；计划是可选能力，因此这里验证的是依据用户回答改变实际正文，不把零计划包装成验证了“重拟计划”。

世界书、记忆、技能的取用另核对了首次请求：被问到的关键事实和技能步骤尚不在消息正文中，工具返回后才进入后续请求。技能第二次读取的是包内引用文件，不能用两次同名工具调用冒充读了两个来源。
