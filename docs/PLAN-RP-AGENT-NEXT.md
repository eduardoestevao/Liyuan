## 一A、第二步的代码维度（用户点名，调查中心）

很多角色卡背后有代码。梨园现有机制与它们的对接点（调查起点，不是结论）：

- `tavern_helper.scripts[]` 页面级脚本宿主（ScriptHost，0×0 同源帧）——悬浮球/交互组件
- 卡内嵌脚本（`extractAuthorScripts`）——MVU prefault 播种、regex 等
- MVU 变量体系（`src/mvu.ts`：变量树、更新规则、schema prefault）——与场记的归属分工
- 状态栏 HTML/CSS/JS（`cardfront.ts` 快照、作者正则、显示管线）
- 作者正则 `regex_scripts`（送模侧 promptRules／显示侧两套应用点）
- 卡档案生成路径（刀3 的「让助手生成」）目前只搬文字——代码资产如何进档案/如何被 agent 理解与修改，是调查要回答的第一个问题

调查产出要求（PLAN-CARD-AUTHORING.md 已有范围）：以真实复杂卡为据，盘点「卡的代码资产清单＋每类资产的执行环境＋agent 读写/验证通道」，再定工具切片。工具归属、代码执行环境与资源组织不在调查前定死。

## 二、第一步：无预设扮演体验

先根据用户指出的问题，复现 pi 回归后梨园实际如何扮演，再做有依据的微调。当前没有收到完整的症状清单，不能把下面的观察面写成已确认缺陷或预定修复方案。

- 观察自然输入下的剧情推进、回应与节奏，工具使用是否服务于正在发生的剧情。
- 观察分段、提问、用户回答、改道与续写的完整体验；保留用户选择及其所属拍次。
- 核对停止、重生成、上一拍修改和继续扮演时，正文、实际送模历史与用户看到的内容是否一致。
- 对每个确认的问题记录复现条件、实际请求/工具/稿件证据、机制归属和改前改后结果；不凭调用次数或一次成功样本宣布体验已经完成。

原计划“只看结构指标”的口径用于之前的底座验收。**本阶段要解决用户实际扮演体验，不能以工具通路已通过来代替体验判断**；同时不引入文风评分器、逐拍审稿模型或强制工具仪式。
