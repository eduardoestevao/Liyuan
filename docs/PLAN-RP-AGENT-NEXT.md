## 二、第一步：无预设扮演体验

先根据用户指出的问题，复现 pi 回归后梨园实际如何扮演，再做有依据的微调。当前没有收到完整的症状清单，不能把下面的观察面写成已确认缺陷或预定修复方案。

- 观察自然输入下的剧情推进、回应与节奏，工具使用是否服务于正在发生的剧情。
- 观察分段、提问、用户回答、改道与续写的完整体验；保留用户选择及其所属拍次。
- 核对停止、重生成、上一拍修改和继续扮演时，正文、实际送模历史与用户看到的内容是否一致。
- 对每个确认的问题记录复现条件、实际请求/工具/稿件证据、机制归属和改前改后结果；不凭调用次数或一次成功样本宣布体验已经完成。

原计划“只看结构指标”的口径用于之前的底座验收。**本阶段要解决用户实际扮演体验，不能以工具通路已通过来代替体验判断**；同时不引入文风评分器、逐拍审稿模型或强制工具仪式。

对照 `PLAN-ROUND-FLOW.md`，继续服务于“看见上文 → 作出选择 → 根据实际变化继续演”，计划是假设。pi `AgentSession` 继续负责模型与工具循环，场记负责定稿后的世界状态记账，世界线导航仍归用户。

## 三、第二步：角色卡制作与代码产品能力

详细调查范围见 [角色卡制作与修改](PLAN-CARD-AUTHORING.md)。这一阶段包括完整卡创作，以及围绕卡开发能实际运行的代码和交互作品。

至少需要调查卡本体与世界书、卡内代码和关联资源、MVU 变量结构/初值/规则、HTML/CSS/JavaScript 状态栏及数据绑定、交互组件，以及跨资源修改后的预览、验证、导入导出完整性。

以真实复杂卡和梨园当前加载、执行、渲染机制为依据，盘点已有能力及缺口，再形成可审阅的工具清单和实施切片。不能仅凭已有“创建角色卡/创建世界书”入口认定此维度完成；工具归属、代码执行环境与资源组织也不能在未调查时先定死。

## 四、第三步：前端优化

面向梨园应用本身的交互、布局、工具过程呈现、稿件与选择操作、刷新和恢复体验进行调整。具体范围依据前两阶段的使用反馈与用户后续指示确定。本阶段不预设重做整套 UI 或更换前端技术栈。
